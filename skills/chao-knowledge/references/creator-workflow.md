# 内容创作与回流

用户只需对话，不需要维护每个阶段目录。Agent 按当次任务读取资料并通过命令登记变化。

## 从资料到选题

1. 读取账号/个人定位、业务产品、目标、受众、表达边界和本次范围的规则。
2. 归档对标正文及作者，区分只存 URL、待转写和真实可读正文。拆解开头、信息顺序、论证、节奏、收尾；分析是 Agent 输出，不能冒充原文。
3. 从用户反馈提取问题和原话，不把单条评论当总体画像；客户信息须脱敏。把分析、洞察与素材保存为标明来源的新资料或项目作品。
4. 提出选题，写明服务哪个用户问题、用了哪份依据。用 save 的“选题池”记录候选，不直接搬用对标标题。

## 作品阶段

`选题池 → 草稿 → 待确认 → 已完成 → 已发布与复盘`

- 初稿调用用户事实、资料与适用规则，外部经历保留归属；保存来源卡和核对项。
- 用户修改创建新版本，使用 --parent 保留版本链。只改本次的意见保存在 change-note；“以后也这样”才进入规则提议/确认。
- 待确认稿列出经历、时效和事实待核对项；未解决不能验收。核对完成后保存新版本并记录 review-quote。
- approve 在用户验收后创建已完成快照，旧稿继续可查。
- publish 在用户已发布后登记平台、受众、时间和可选链接，创建发布快照；脚本不会自动上传或发布。
- 后续修改已发布内容仍先创建草稿，不改写历史发布记录。

## 数据与评论回流

feedback 保存同一作品每个窗口的数据快照。评论正文按“用户反馈”资料导入、脱敏，再与项目/作品复盘关联。未知数据留 null，不能用 0 代替；采样口径、平台、观察时间和作品时长要一致。

复盘内容用 experience 记录：

- observation：实际看到了什么；
- hypothesis：可能原因，仍待验证；
- experiment：下一次准备验证什么，不代表脚本会执行；
- validated：至少两件独立已发布作品的可比反馈，加用户确认和明确范围。

同一作品的二稿、发布快照或不同时间数据不算两次独立验证；单条表现好不建立因果。已验证经验也不自动形成规则。新任务的 context 可重新读到适用经验、相关作品和资料；Agent 要检查状态和遗漏。

## 归属与质量

可以借鉴结构、主题与方法，使用自己的表达。第一人称经历、收入、客户、成绩必须有用户明确提供的对应依据。作者、同事、团队与用户本人分开。缺证据就删除或标待核对，不逐句同义替换，不承诺播放量或收益。
