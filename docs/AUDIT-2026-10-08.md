- 比较区分脚本已经实现的行为和要求 Agent 遵守的流程。没有运行 Shengjiang 的真实客户端旅程，不给它或本候选编造 GUI PASS。

- 本次修改是独立分支的 v0.3.4 开发候选，尚未发布；普通用户的一句话安装仍指向正式 Release。

## 结论

Chao 已经具备独立档案、来源归属、任务上下文、分场景规则、作品版本、发布登记和反馈经验。短板主要在新用户如何完成第一件事、如何找回积累的内容、如何接入一批旧资料和如何理解异常。继续增加目录数量不能解决这些问题。

用户可以从空文件夹开始正常对话，但“零学习成本”尚不成立：安装发现依赖宿主，非文本提取依赖宿主能力，资料必须登记，换对话必须选择同一工作区，手改投影需要同步处理。公开介绍应让用户知道最少的必要动作，而不是把内部命令当成使用门槛。

## 已复现并修正

| 问题 | 原版证据与用户影响 | 候选处理 |
|---|---|---|
| P1：启动入口写死项目安装路径 | `kb.py` 的 BOOT 要求先读 `.codebuddy/skills/...`；用户级安装后该目录可以完全不存在 | 新入口依据宿主实际加载路径；init 备份并更新逐字匹配的旧模板，保留用户手改块及块外文字 |
| P1：同秒导入的“最近资料”顺序错误 | `navigation_document` 用随机 ID 打破秒级时间并列；控制 UUID 后可稳定复现新资料 9 不在最近 8 条中 | 使用持久化登记顺序处理同秒并列；检索相关度相同时也优先新记录，不修改 state schema |
| P2：超过 8 条后缺少完整可读入口 | 地图只保留 8 条，分类目录内是 `_资料/内部编号`；用户不易找到更早的内容 | 增加全部资料、分类资料及作品版本索引，地图提供入口；只投影标题/状态/链接，不复制正文 |
| P2：普通用户被暴露内部编号与参数 | Skill 要求交付“来源 ID”，长期要求投影直接显示规则 ID | 默认交付标题、可点击路径和中文范围；规则投影去掉 ID，机器状态/API 保留标识 |
| P2：首次任务与完成条件不够清楚 | 只搭基础结构后容易继续追问；默认风格等偏好可能被当成必须解决的事实项 | 明确用户只搭结构就停；只将实际采用却未核实的事实列为必需核对项；不削弱 approve 的事实核对保护 |
| P2：使用指南与已实现的 health 行为不一致 | `USAGE.md` 说保存报告只新增报告，但代码也会更新未手改地图的摘要 | 对齐实际范围：保存报告及摘要，不覆盖手改或修复缺失结构 |

没有改写真实用户的 AGENTS 或知识库；升级行为仅在合成目录和已发布 v0.3.3 包生成的测试库中验证。

## 与 Shengjiang 的实质差距

| 维度 | Chao v0.3.3 / 本候选 | Shengjiang 源码所支持的判断 | 应采取的方向 |
|---|---|---|---|
| 空库首次使用 | 三项背景即可开始；中文档案与地图较直观，本候选把首次任务放到 README 安装后 | 通用/creator 两套模板，先预览再应用；目录与协作职责说明完整，但新手要理解模式和若干英文核心文件 | 保持 Chao 的简短对话入口，把技术安装说明折叠；不要求小白选择内部模式 |
| 接入已有目录 | 可保留无冲突的原文件；同名业务目录会拒绝 init；没有任意旧库的目录映射导入 | 明确区分空库、已有资料、已有导航三种情况；初始化脚本跳过现有文件，Agent 负责映射和补入口 | **主要差距**：做指定目录的只读预览、冲突说明和逐批接入；不先自动搬家 |
| 批量资料 | 当前 `ingest` 逐文件，明确的大小/格式/链接限制；没有扫描与批量计划命令 | `scan_materials.py` 已实现文件或目录清单、类型、大小、时间和敏感名称标记；真正理解/落位仍依赖 Agent | **主要差距**：先补可恢复、有进度和逐项结果的导入计划，不能把扫描清单称为读懂正文 |
| 内容查找 | 地图最近 8 条；本候选补全量和分类索引；有预算的中文双字/英文关键词检索 | 有总索引与区域索引模板，强调原文与路径；并非内置向量检索服务 | 先确保找得到已登记内容，再考虑大量资料下的索引规模与性能 |
| 内容创作流程 | save/approve/publish 在脚本中执行版本、来源与核对约束，保留历史和分支 | creator 文档和模板细分定位、调研、洞察、素材、审核、定稿、待发布；许多流转依赖 Agent 按文档执行 | 我们不缺主要阶段；应补可直接使用的任务交付模板与实例，不为对齐目录而加空阶段 |
| 纠正复用 | 有临时 change-note、长期规则和经验；`AI纠正记录.md` 主要显示规则动作；context 的作品摘要未带 change-note | MEMORY_LOG 记录纠正并计同类次数，达到三次提议规则，仍需确认；主要是 Agent 工作约定 | **主要差距**：让相同场景的临时纠正在后续任务中可见；次数只提示，不自动升级为规则 |
| 日常维护 | health 有哈希、投影漂移、待提取、规则冲突、积压等；默认只读 | 有任意既有目录的断链/导航/根部散落检查，以及每周/结构变化后巡检的说明 | 增强维护提示与问题的自然语言下一步，保留“未授权不自动修复” |
| 稳定性与保护 | 持久 OS 锁、事务暂存/恢复、原件及来源哈希、跨平台 CI；这些在脚本中可直接验证 | 所审三个 knowledge 脚本中未见同等的多文件事务与 OS 锁；现有 CI 配置为 Ubuntu/Python 3.11 | 保留现有保护，不为了减步骤取消真实确认；不能据此断言对方在其他平台不能运行 |
| 视频/网页采集 | 本 Skill 不内置抓取或转写，交给宿主 | knowledge 同样依赖宿主提取；仓库另有付费 API 的 research Skill | 不把 research 的能力算成 knowledge 自带；先明确输入格式和读取范围，再谈可选集成 |

Shengjiang 的优势是既有资料接入与维护方法更完整。Chao 的优势是来源、状态流转和数据保护有更多确定性脚本支撑。两者都不能仅凭目录和宣传证明普通用户的客户端体验。

## 仍需处理，未冒充完成

1. **安装决策与耗时**：统一用户级/项目级的选择与发现诊断，减少安装后才让用户理解两个副本；必须等允许客户端验收后验证。
2. **批量接入与老文件夹兼容**：只读清单、大小/类型/归属预览、逐项失败说明、去重与继续导入；当前没有这套执行器。
3. **纠正的跨任务复用**：在相关任务上下文中纳入临时修改记录，并明确作用范围；当前不把所有临时修改变成全局偏好。
4. **文案约定不等于模型必然遵守**：本次“少内部术语、先交草稿”的改动是 Agent 指引，需要后续自然语言客户端回归确认。
5. **长库性能**：全量 state/投影仍随写入重算，检索最多检查 1000 条/20 MiB；新索引沿用 2 MiB 上限，不称为无限规模知识库。
6. **发布验证脚本**：`tools/verify_cli.py` 当前对比远端 main 与本地 manifest；候选分支与 main 不同会拒绝通过。正式整合前应让该校验针对明确提交，不能拿旧 main 的成功证明候选。
7. **证据台账**：原 VALIDATION 的 PENDING 不能当失败，也不能由录屏成功替代三轮、旧版更新和 direct 5xx fallback；本轮没有执行这些客户端项。
8. **宿主呈现与语义范围**：索引链接已按文件所在目录验证目标存在，但 WorkBuddy 预览中的真实点击跳转仍需客户端验证。范围仍为精确匹配；本次只要求 Agent 复用已有范围值，没有新增同义词推断引擎，不能声称所有自然语言说法都会自动命中。

建议顺序：先整合本次可发现性与启动修正，再做批量资料接入，随后补纠正复用与维护提示。暂不增加向量数据库、付费采集、自动发布或新的事实源。
